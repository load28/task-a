# 계획 변경을 수용하는 증분 실행 설계

상태와 무관하게 계획 변경을 접수한다. 이전 실행과 결과는 보존하고, 새 계획에 필요한 작업과 증거만 선별하여 재사용한다. 이 문서의 1~4절은 목표 설계다. 아래 구현 현황은 실제 지원 범위와 남은 경계를 구분한다.

## 1. 계획·명세·실행·결과의 수명을 분리한다

현재 Task 한 개를 수정하고 reopen하는 방식 대신 다음 관계를 둔다.

```text
WorkPlan
  ├─ PlanRevision 1 ── RevisionBinding ── TaskSpecVersion A1
  └─ PlanRevision 2 ── RevisionBinding ── TaskSpecVersion A1 또는 A2
                                            │
                                         ExecutionAttempt
                                            │
                                  StageCheckpoint / Artifact / Evidence
```

- `WorkPlan`: 장기간 유지되는 사용자 목표의 식별자다. `activeRevision`과 `proposedRevision`을 분리한다. 목표 자체의 내용도 개정에 속한다.
- `PlanRevision`: 요구사항·제약·계획 노드·부모 관계·의존성의 불변 스냅샷이다. 전체 실행이 완료됐어도 새 개정을 만들 수 있다. 기존 개정의 완료 사실은 유지한다.
- `TaskSpecVersion`: 안정적인 논리 태스크 ID에 연결된 불변 명세 버전이다. 요구사항, 입출력 계약, 완료 조건과 단계 명세를 갖는다. 분할·병합에는 명시적인 이전 노드 매핑을 둔다.
- `RevisionBinding`: 특정 개정이 사용하는 명세·실행·결과 버전을 지정한다. 이전 실행의 성공 여부와 새 개정에서 결과를 사용할 수 있는지는 다른 속성이다.
- `ExecutionAttempt`: 실제 실행 한 번이다. 명세 버전, 정확한 입력 결과물 버전, 환경 digest, Pod/PVC, 실행 토큰, 단계 상태를 고정한다. 중단·실패·완료 이력을 덮어쓰지 않는다.
- `Artifact`와 `Evidence`: 내용 해시, 생산 실행, 사용한 입력 버전, 검증 조건을 가진 불변 결과다. 재사용은 복사가 아니라 새 개정에서 기존 결과를 참조하는 것이다.

실행 상태는 `queued/running/suspending/suspended/succeeded/failed`로, 개정 내 유효성은 `valid/needs-validation/invalid/excluded`로 분리한다. 예를 들어 A1은 실행에 성공했지만 A2의 요구사항에는 맞지 않을 수 있다. 반대로 이전 계획에서 중단된 작업의 조사 결과가 새 계획에 유효할 수 있다.

루트의 완료 여부는 해당 개정의 유효한 바인딩, 완료 조건, 통합 검증으로 계산한다. 삭제된 노드는 역사에 남지만 새 개정의 완료 조건에서 제외한다. 의존성은 개정별 정확한 목록으로 교체하여 삭제된 간선이 남지 않게 한다. 과거 결과를 보존하면서도 과거 요구사항이 새 루트를 막지 않도록 한다.

## 2. 상태 대신 변경 영향과 증거로 재사용을 판단한다

계획 변경은 우선 요구사항·계약의 구조화된 차이로 변환한다. 문구 유사성이나 태스크 제목만으로 재사용을 결정하지 않는다.

각 단계에 소비하는 요구사항/제약 ID, 입력 계약, 파일·결과물 의존성, 생산 결과와 검증 조건을 선언한다. 루트 제약 변경은 이를 상속·소비하는 하위 단계까지 전파한다. 이름·설명 정리와 같은 표시 변경은 실행 명세 지문에서 제외한다.

작업 상태에 따른 처리:

| 이전 상태 | 유효한 입력·명세가 유지되는 경우 | 관련 요구사항·입력·환경이 변경된 경우 |
|---|---|---|
| 완료 | 결과를 참조하고 유효한 검증 증거를 사용한다 | 유효한 단계 결과는 보존하고 영향받은 검증·작업만 다시 수행한다 |
| 진행 | 같은 실행을 계속 관찰하고 새 개정의 결과 후보로 연결한다 | 영향을 받는 실행만 중단하고 일관된 체크포인트를 확보한다 |
| 중단·실패 | 중단 원인과 부분 변경을 확인하고 미완료 단계부터 재개한다 | 유효한 단계 결과를 가져와 새 명세의 실행을 만든다 |
| 미시작 | 기존 실행 대기를 새 개정에 연결한다 | 새 명세로 대기 작업을 교체한다 |

새 계획에서 불필요한 작업은 상태에 관계없이 제외한다. 진행 중이면 종료를 요청하고 결과는 보관한다. 요청 취소 자체가 파일 삭제를 뜻하지 않는다.

단계의 재사용 키는 다음처럼 계산한다.

```text
workKey = hash(
  유효 요구사항·제약·입출력 계약,
  관련 입력 결과물 내용 해시·실제 읽은 코드 의존성,
  단계 실행 정의·필요 도구/환경 버전
)
evidenceKey = hash(
  검증 대상 결과물 해시,
  검증 명령·완료 조건·관련 환경·통합 상대 버전
)
```

계획 개정 번호와 unrelated 태스크 변경은 키에 넣지 않는다. 전체 저장소 커밋만 키로 쓰면 무관한 파일 수정에도 모든 캐시가 무효화되므로 관련 입력을 추적한다. 다만 의존성 추적이 불완전하면 범위를 넓혀 검사한다. 입력이 같다는 것만으로 비결정적 명령이나 외부 쓰기의 재실행을 생략하지 않는다. 외부 데이터·조사에는 출처 버전, 관측 시점, 유효 기간 및 필요 시 재확인 조건을 둔다.

변경 영향은 의존 그래프를 따라 전파하되, 새 생산 결과의 내용과 계약이 이전과 같아지면 그 경계에서 불필요한 후속 재실행 전파를 멈춘다. 결과가 바뀌었지만 소비 계약이 호환되는 경우에는 기존 구현을 후보로 유지하고 영향받은 테스트만 실행한다. 계약이 바뀌면 소비자 구현을 검사한다. 계약에 표현되지 않은 숨은 의존성이 의심되면 검사 범위를 넓힌다.

완료 상태는 캐시 적중의 증거가 아니다. 코드 결과 재사용과 검증 결과 재사용은 따로 판단한다. 예를 들어 출력 코드는 같아도 통합 상대가 바뀌면 통합 테스트는 다시 필요하다. 테스트는 실제 실행기로 수행하며 LLM에 같은 구현을 다시 생성하게 하지 않는다.

## 3. 계획 변경은 지속 가능한 전환 작업으로 처리한다

변경 요청은 모든 상태에서 즉시 접수할 수 있다. 새 계획의 실행 시작은 필요한 종료·복구 확인을 기다릴 수 있으며, 이 대기를 실패로 취급하지 않는다.

```text
변경 접수 → 새 개정·영향 분석 → 전환 의도 저장 → 영향 범위 차단
         → 종료/체크포인트 확인 → 재사용 바인딩·입력 구성
         → 활성 개정 전환 → 필요한 실행만 배치 → 증분 검증
```

`Transition`에 기준 개정, 목표 개정, 실행 토큰, 대상별 keep/adopt/suspend/validate/replace/exclude 결정, 실제 처리 상태와 재시도 키를 저장한다. 분석 중 기존 작업이 끝나거나 다른 변경이 도착할 수 있으므로 적용 시 기준 개정과 결과 버전을 다시 확인한다. 오래된 분석으로 활성 계획을 덮어쓰지 않는다.

영향 없는 실행은 계속 진행한다. 영향을 받는 작업과 그 결과를 소비할 예정인 새 실행만 차단한다. 영향이 불명확하면 관련 범위를 우선 보류하고 판정 후 해제한다. 변경 초안 작성과 실행 허가는 구분하고, 사용자 변경 지시가 허용한 범위를 승인 기록에 반영한다. 단순 접수 상태를 자동 승인으로 취급하지 않는다.

DB 트랜잭션에는 전환 의도와 외부 명령 outbox를 기록한다. Pod 종료 같은 외부 작업을 DB 트랜잭션 안에서 기다리지 않는다. 컨트롤러는 요청을 반복 전달하고 실제 상태를 관찰하며 완료 표시를 한다. 재시작 후에도 같은 전환을 계속 수행한다. 빠르게 연속된 변경은 아직 실행하지 않은 전환을 최신 개정으로 대체할 수 있지만, 이미 진행 중인 종료·스냅샷은 관찰을 마치고 안전한 상태로 수렴시킨다.

**늦게 도착한 완료 결과:** 모든 보고는 `attemptId`, 명세/입력 버전, 실행 토큰을 포함한다. 과거 실행의 보고는 이력과 결과 후보로 저장하되 새 계획을 완료시키지 못한다. 새 개정에서 사용할 결과인지 입출력 키와 바인딩을 확인한 뒤에만 채택한다. 그대로 유지된 실행은 동일한 입력을 증명하고 새 개정에 명시적으로 채택할 수 있어 중단·재시작과 재프롬프트를 피한다.

**실행 및 쓰기 소유권:** 실행 권한과 결과 채택 권한을 구분한다. 영향받은 이전 실행은 공유 결과 반영·통합 권한을 먼저 회수한 뒤 중단한다. 이전 Pod가 종료되기 전 같은 쓰기 환경에 새 Pod를 붙이지 않는다. 노드 단절 상황은 API상의 삭제만으로 실제 종료를 가정하지 않고 스토리지 fencing 또는 운영자 확인을 요구한다. 이전 실행의 저장소 밖 쓰기·push·배포는 권한 검사와 멱등성 키를 통과하는 경로로 제한한다.

**부분 작업 재사용:** 종료가 확인된 PVC에서 체크포인트 manifest와 Git diff/결과물을 확정한다. 지원되는 스토리지에서는 스냅샷을, 아니면 중단된 볼륨의 검증된 파일 복사나 Git bundle을 사용한다. 새 명세는 새 attempt와 작업 공간을 가지며 유효한 결과만 가져온다. 옛 코드 위에 새 코드를 계속 덧붙이는 대신 새 목표 기준 코드에 선택된 변경을 적용하고, 제거된 기능이 남지 않는지 확인한다. 충돌은 별도 해결·검증 대상으로 둔다. 삭제 정책은 모든 활성 참조가 사라진 뒤에만 데이터를 정리하도록 한다.

## 4. 토큰은 변화의 의미 판단에만 우선 배정한다

실행 상태 조회, 버전 비교, 영향 전파, 캐시 조회, 체크포인트 복원, 명령 재시도는 코드로 처리한다. 의미가 불명확한 요구사항 변경과 실제 수정이 필요한 단계에만 모델을 호출한다. 모든 태스크마다 재사용 판정을 위한 모델을 별도로 실행하지 않는다.

모델 입력은 전체 대화 재전송 대신 다음의 최소 재개 패키지로 구성한다: 현재 요구사항·변경 차이, 해당 단계의 고정 입력 참조, 채택한 결과 요약, 무효화된 가정과 부분 작업 위치, 아직 충족되지 않은 완료 조건. 필요할 때만 원문·결과물·최근 로그를 추가로 가져온다. 요약에는 원본 버전 참조를 남겨 손실된 내용을 확인할 수 있게 한다.

실행 재개와 모델 대화 재사용도 구분한다. 명세가 같으면 기존 세션을 재사용할 수 있다. 방향이 크게 달라졌으면 기존 결과물과 축약된 재개 패키지를 새 세션에 전달해 오래된 지시가 계속 적용되는 것을 막는다. 같은 명령이라도 중단된 단계에 외부 부작용이 있었으면 별도 확인 없이 반복하지 않는다.

단계 경계는 결과를 독립적으로 검증·재사용할 수 있는 단위로 둔다. 모든 도구 호출을 별도 태스크로 나누지 않는다. 조사, 계약/설계, 독립 구현 결과, 검증 결과 등의 경계에서 저장한다. 저장 주기는 재실행 비용과 체크포인트 비용을 기준으로 설정한다. 실제 입력/출력 토큰, 캐시 적중, 재사용 결과 수, 재실행 단계 수, 검증 비용을 측정하여 절감 효과를 판단한다.

예를 들어 조사 A 완료, API 구현 B 진행, 화면 C 중단, 통합 D 미시작 상태에서 API 응답 계약이 바뀌면 A의 관련 가정이 유지되는지 확인해 재사용하고 B의 영향 단계만 멈춘다. C의 화면 자산은 가져오되 데이터 연결 단계는 새 계약 기준으로 수행한다. D는 새로 채택된 결과 버전 조합으로 검증한다. API 출력이 실제로 이전과 동일한 경우에는 C의 불필요한 구현 재작업을 생략할 수 있다.

검증 기준은 상태 조합 자체보다 불변 조건이다. 완료/진행/중단/대기 혼합 상태에서 변경·삭제·분할·병합·연속 변경과 늦은 완료 보고를 주입한다. 전환 각 단계에서 서비스/컨트롤러를 종료하고 재시작한다. 새 루트는 새 개정의 결과만 참조해야 하고, 유효한 완료 단계는 다시 실행되지 않아야 하며, 같은 작업 공간에 동시 쓰기 실행이 생기지 않아야 한다. 완료된 루트도 새 개정의 미완료 작업을 가진 활성 목표로 이어갈 수 있어야 한다.

## 구현 현황

### 개정과 선택적 전환

`RevisionCoordinator`는 활성 개정과 최신 제안 개정을 구분한다. 목표·요구사항·제약·노드 명세·의존성을 비교하며 완료된 루트도 새 개정을 받는다. 변경된 명세에는 새 태스크 ID를 만들고 이전 태스크와 결과를 보존한다. 제외된 태스크·의존성·요구사항·통합 집합은 현재 완료 조건에서 제외한다. 변경된 하위 노드를 포함한 그룹의 통합 증거도 무효화한다.

전환 대상과 실행 토큰은 SQLite에 먼저 저장한다. 영향받은 실행을 차단하고 종료가 확인되면 활성 개정을 전환한다. 서비스 재시작 후 전환을 이어가며 연속 변경은 이전 종료 의도를 계승한다. 무관한 실행은 유지한다. `work_plan_transition_status`는 조회하고 `work_plan_reconcile`은 종료 관찰과 전환을 진행한다. 로컬 host 서비스는 알려진 workspace의 전환을 반복 처리한다. 원격 Graph MCP에서는 호출자가 reconcile을 반복해야 한다.

Kubernetes는 Suspended 관찰, native OpenCode는 실제 sessionId의 종료·도구 실행 상태 관찰이 필요하다. 작업자 신원을 모르면 전환은 대기한다. 기존 host의 일반 `steer` 명령은 기존 실행 취소 경로이며, 선택적 전환은 위 계획 개정 도구 경로를 사용한다.

### 이전 실행 보고와 고정 컨텍스트

`task_start`는 실행 토큰과 정확한 입력 결과물 버전 및 컨텍스트 스냅샷을 저장한다. 개정 관리 태스크는 완료·실패·결과물 보고에 해당 attemptToken을 전달한다. 이전 토큰의 완료·실패는 이력으로 보관하며, 이전 결과물은 별도 이름으로 보존하고 현재 출력에 연결하지 않는다. 폐기된 통합 실행의 늦은 결과도 현재 그래프에 승격하지 않는다.

재실행 컨텍스트는 현재 명세, 고정 입력 및 재사용 후보의 결과물·실행 참조를 포함한다. 전체 과거 대화를 재전송하지 않는다. 이 토큰 검사는 그래프 반영 경계이며 저장소 밖 임의 push·배포 같은 외부 부작용을 차단하는 범용 권한 게이트는 아직 구현하지 않는다.

### 태스크·단계 재사용

명세가 동일한 완료 태스크는 이전 결과를 참조한다. 입력 변경으로 재검증이 필요한 태스크에는 이전 작업 후보를 전달한다. `task_reuse`는 유효한 이전 검증과 동일한 입력 내용·계약을 확인한 경우에만 결과를 채택한다. 판정 실패 시 reused=false를 반환하여 구현 또는 검증을 진행하게 한다. 조회 도구는 결과를 자동 채택하지 않는다.

Kubernetes 단계에 `outputs`, `inputDigest`, `dependsOn`을 선언하고 새 인스턴스의 `reuseSources`로 이전 태스크·단계를 지정한다. 종료된 이전 PVC는 읽기 전용으로 연결한다. 이미지·명령·명시적 입력 지문과 출력 manifest 해시가 맞으면 선언된 출력만 새 PVC로 가져오고 명령을 생략한다. 이전 방향의 미완성 구현 전체를 복사하지 않는다. 가져온 결과는 새 PVC에도 독립적인 캐시로 보존한다.

교차 인스턴스 재사용에는 명시적 inputDigest가 필수다. 호출자가 실제 요구사항·코드·외부 입력·환경을 모두 포함해 계산해야 한다. 실제 파일 읽기 자동 추적, 외부 데이터 유효 기간 판정, 충돌하는 코드 패치 자동 병합, 토큰 절감 계측은 아직 구현하지 않는다. 중단된 명령은 프로세스 메모리를 복원하지 않으며 체크포인트와 파일을 기준으로 다시 호출한다.

### 검증

`npm run check`로 타입 검사와 전체 테스트를 실행한다. 개정 테스트는 혼합 상태, 완료된 루트 변경, 표시 변경, 연속 변경과 DB 재시작, 과거 결과 재채택, 입력 고정, 오래된 실행의 결과물·실패 격리, 루트 제약 교체를 검증한다. 단계 테스트는 유효 캐시 재사용·입력 변경·손상 거부를 검증한다.

`npm run test:revisions:kubernetes`는 실제 kind에서 변경 대상 Pod만 중단하고, 무관한 Pod UID를 유지하며, 그래프 재시작 후 새 명세·PVC에서 조사 결과만 재사용하는지 검증한다. 이 테스트의 실행 단계는 셸 명령이며 실제 모델 호출과 토큰 사용량은 측정하지 않는다.
