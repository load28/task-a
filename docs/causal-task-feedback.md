# 원인 태스크로 돌아가는 수정 흐름

문제를 발견한 위치와 수정 책임을 분리한다. QA, 구현, 설계, 통합 등 어떤 태스크도 문제를 기록할 수 있다. 모델이 원인을 진단하고, 엔진은 산출물 생산자와 입력 이력으로 그 진단의 연결 관계를 검증한다. QA의 파일 수정 권한을 일괄 금지하는 방식은 사용하지 않는다.

## 문제 기록과 원인 확정

`task_issue_report`는 발견 태스크, 재현 근거, 관찰한 산출물의 정확한 버전을 저장한다. `task_complete`의 검증 실패와 `integration_report`의 실패도 자동으로 기록한다. 일반적인 실행 중단인 `task_fail`은 원인 확정으로 취급하지 않는다. 실제 결함을 발견했으면 별도로 문제를 기록한다.

`task_issue_route`는 관찰한 산출물 또는 그 입력 이력의 담당 생산 태스크로 문제를 보낸다. 아직 산출물을 게시하지 못한 경우에는 발견 태스크 자신 또는 선행 의존 태스크를 근거와 함께 지정한다. 원인이 불명확하면 `reported` 상태로 남긴다. 모델이 진단해야 하는 의미적 원인을 엔진이 추측하지 않는다.

## 책임과 작업공간을 유지하는 새 실행

수정은 승인된 목표를 유지하는 내부 계획 리비전으로 처리한다. 원인 담당과 영향을 받는 후속 작업만 교체하고, 무관한 실행과 결과는 유지한다. 실행 중인 대상은 먼저 결과 제출 권한을 차단하고 실제 종료를 확인한 뒤 교체한다. `transitionId`는 기존 `work_plan_reconcile` 경로를 사용한다.

실행 중 추가 분해한 하위 태스크도 기존 책임과 의존 관계를 복제한다. 각 교체 태스크의 문맥에는 이전 실행, 산출물, 문제 근거가 들어간다. 계획 없이 생성했던 그래프도 기존 실행을 보존한 채 리비전 관리에 편입한다.

Kubernetes에서는 기존 인스턴스 바인딩이 있는 수정 태스크에 자신의 `restoreFromTaskId`를 자동 지정한다. 완료된 작업은 체크섬으로 검증한 전체 아카이브에서 복원한다. 실패·중단 작업은 종료가 확인된 원본 PVC를 읽기 전용으로 마운트하고 새 PVC에 복사한다. 코드, 미커밋 파일, Git 이력, 모델 세션을 유지한다. 복원 소비자가 사용하는 동안 원본 재개와 데이터 정리를 보류한다.

## 새 버전의 전파와 해결 판정

산출물 입력을 생략하면 실행 시 고정한 입력 버전을 기본 이력으로 저장한다. 수정된 버전은 후속 작업과 통합 검증에 전달한다. 후속 입력 내용과 명세가 동일하면 검증된 결과를 모델 실행 없이 재사용하고, 새 입력을 가리키는 산출물 버전을 게시한다. 발견 태스크와 원인 담당의 수정 실행은 이 재사용으로 건너뛰지 않는다.

`task_issue_resolve`는 담당 태스크가 새 버전을 게시했는지, 영향받는 작업이 완료됐는지, 최신 의존 버전 또는 실제 코드 해시가 동일한 입력으로 검증했는지, 기존 영향 통합 경계가 다시 통과했는지 검사한다. 해결되지 않은 문제는 루트 완료를 막는다. 이전 실행의 늦은 완료·통합 결과는 현재 결과를 승격하지 않는다. 입력 변경의 전파와 재사용 조건은 [코드 해시 기반 Push/Pull 실행](input-signals.md)을 따른다.

계획을 다시 바꿔도 미해결 수정 의무는 유지한다. 승인 대기 중인 계획이 있으면 먼저 해당 전환을 처리한 뒤 문제를 라우팅한다. 필요한 책임 자체가 삭제된 경우 과거 검증으로 문제를 닫지 않고 재진단을 요구한다. 이 도구는 테스트 실행 사실을 의미적으로 판별하지 않으므로 관리자가 실제 실행 근거를 제출해야 한다.

## 검증

`npm run check`로 상태별 교체, 원인 이력, 무관한 작업 보존, 지연 결과 격리, 하위 분해 복원, 계획 변경, 통합 재검증을 검사한다.

```sh
TASK_INSTANCE_CONTEXT=kind-task-agent-local \
TASK_INSTANCE_NAMESPACE=task-agent \
TASK_INSTANCE_IMAGE=task-agent-instances:feedback \
npm run test:feedback:kubernetes
```

2026-09-08 실제 kind 검증은 모델 대신 결정적인 Node 명령으로 결함을 주입했다. 소비 Pod에서 `1 !== 2` 실패를 확인한 뒤 생산 태스크의 아카이브를 복원해 `2`로 수정했다. 소비 태스크는 실패 당시 PVC의 테스트 파일을 복원하고 새 산출물 버전으로 통과했다. 중간 MCP 연결 재생성 후에도 동일 문제와 리비전으로 진행했다. 성공한 작업의 Pod/PVC는 아카이브 후 제거했고, 테스트 종료 시 실패 작업 리소스도 정리했다.
