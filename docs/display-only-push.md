# 모델 실행 없는 태스크 보고 푸시

상태: 표시 클라이언트의 구현 범위 결정 필요. 현행 실행 서비스에는 아직 적용하지 않았다.

## 요구사항과 클라이언트 확인

하위 태스크가 보낸 진행·문제 보고를 사용자가 즉시 읽을 수 있어야 한다. 보고 수신은 모델 입력, 새 대화 턴, 자동 복구 또는 승인으로 변환하지 않는다. 사용자가 후속 지시를 보냈을 때만 기존 명령 경로로 처리한다.

2026-09-09 설치 버전은 Codex CLI 0.153.4와 Claude Code 2.1.261이었다. 테스트 MCP를 각 CLI에 연결하고 초기화 완료 후 `notifications/message`를 보냈다. 두 대기 화면에 테스트 본문이 표시되지 않았다. 초기화·도구 목록 요청은 테스트 서버에서 확인했다. 이는 일반 MCP 알림의 표시 시험이며 모든 비공개 확장 기능의 부재를 증명하는 것은 아니다.

Codex 공식 저장소의 [logging_client_handler.rs](https://github.com/openai/codex/blob/main/codex-rs/rmcp-client/src/logging_client_handler.rs)는 `notifications/progress`와 로그 알림을 tracing에 기록한다. 설치된 바이너리에는 별도 앱 서버 진행 이벤트 형식도 있어 공개 main 코드만으로 설치 버전의 모든 화면 동작을 단정하지 않았다. 진행 도구를 호출하는 추가 TUI 시험은 자동 승인 검토가 모의 모델의 응답을 유효한 검토 JSON으로 해석하지 못해 거절했다. 해당 도구는 실행되지 않았고 보호 설정도 변경하지 않았다.

[Claude MCP 문서](https://code.claude.com/docs/en/mcp)는 실행 중인 도구의 진행 알림 및 장시간 호출의 백그라운드 전환을 설명한다. 이는 대기 중인 대화창에 임의의 보고를 추가하는 표시 전용 수신 인터페이스와 다르다. [Claude Channels](https://code.claude.com/docs/en/channels-reference)는 수신 이벤트를 모델 문맥에 넣으므로 이번 요구사항의 표시 경로로 사용하지 않는다.

## 이벤트 경로와 명령 경로

```text
태스크 작업자 / 실행 컨트롤러
  └─ 보고 발행 → 작업자 outbox → 보고 수집 서비스 → 영속 이벤트 스트림
                                                    └─ 표시 구독 → 화면 렌더러

사용자 지시 → 기존 호스트 훅 / 제어 API → 태스크 실행 서비스
```

보고 경로는 명령·스케줄러·모델 실행기를 호출할 권한을 갖지 않는다. 현재 `HostService.drain()`의 상태 검사 결과를 주기적으로 포장하는 것으로 푸시를 대체하지 않는다. 작업자는 실제 단계 시작·진행 보고·검증·오류 시점에 이벤트를 발행한다. 컨트롤러는 작업자 프로세스가 보고하지 못한 시작 실패·종료·연결 문제를 발행한다.

수집 서비스는 영속 저장 후에 발행 확인을 반환한다. 브라우저 또는 네이티브 화면은 연결을 유지한 SSE 스트림에서 이벤트를 받는다. 연결 복구는 이벤트 커서부터 재생하며, 정상 연결 중 상태 폴링은 사용하지 않는다. 수동 상태 조회는 별도 진단 기능으로 유지한다.

## 영속화와 표시 계약

보고에는 다음 정보를 보존한다.

| 영역 | 필드와 규칙 |
|---|---|
| 식별·소유권 | eventId, workspaceId, requestId, taskId, attemptId, producerSequence; 발행자의 태스크·실행 세대와 일치해야 한다. |
| 보고 내용 | 종류, 발생 시각, 현재 작업, 요약, 확인된 근거, 복구 시도, 사용자 판단 필요 여부; 명령·종료 코드·오류 요약은 비밀값을 제거한다. |
| 전달 순서 | 수집 서비스가 workspace별 순번을 배정한다. eventId와 발행자 순번으로 중복 발행을 제거하며 오래된 실행 세대가 최신 상태를 덮어쓰지 못한다. |
| 표시 확인 | 구독자별 마지막 렌더링 커서를 저장한다. 전송 완료와 화면 표시 완료를 구분하며, 재접속 시 중복 카드를 만들지 않는다. |

서버와 화면은 `displayOnlyTaskReportsV1` 지원 여부를 협상해야 한다. 지원하지 않는 클라이언트에는 표시 완료를 기록하지 않는다. MCP의 `notification()` 쓰기 완료를 사용자 수신 확인으로 취급하지 않는다. 여러 세션이 같은 프로젝트를 열어도 구독 범위 밖 요청이나 다른 프로젝트 보고를 섞지 않는다.

표시기는 보고의 원문을 안전한 텍스트로 렌더링한다. 셸 명령·제어 문자·모델 프롬프트로 실행하지 않는다. 상세 보고를 합성하거나 요약하기 위한 모델 호출도 하지 않는다. 메시지 압축과 모델 문맥은 이벤트 저장소 및 렌더링 커서에 영향을 주지 않는다.

## 구현 경계와 수용 검사

서버 측 구현 경계는 `packages/task-reports`의 이벤트 계약·저장소·구독, `packages/task-instances`의 발행자 outbox, `packages/host-integration`의 프로젝트·요청 구독 연결이다. 화면 표시 어댑터가 없으면 이 경로만 배포해도 사용자의 요구는 충족되지 않는다.

원본 CLI 화면을 필수로 유지하려면 각 클라이언트가 표시 전용 이벤트와 렌더링 확인 인터페이스를 제공해야 한다. 자체 대화 화면을 허용하면 Codex 앱 서버·Claude 실행 인터페이스와 보고 스트림을 같은 화면에 연결할 수 있다. 기존 CLI의 stdout·TTY나 대화 기록 파일을 외부에서 조작하는 방식은 사용하지 않는다.

완료 조건은 실제 화면에서 다음을 확인하는 것이다.

- 클라이언트가 유휴 상태여도 보고가 표시되고, 수신 전후 모델 호출 수가 증가하지 않는다.
- 연결 끊김·프로세스 재시작·대화 압축·중복 발행·구독자 재접속 이후에도 보고가 누락되거나 중복 표시되지 않는다.
- 작업자 오류 보고에 실패 지점·근거·복구 시도가 표시되며, 보고 수신만으로 작업 상태나 승인 상태가 변경되지 않는다.
- 실제 Codex·Claude 표시 어댑터 각각을 검증하고, 미지원 화면을 정상 전달 상태로 표시하지 않는다.
