# Superpowers 인터뷰와 AX 계획 연결

새 목표, 새 프로젝트, 기능·구조 변경을 계획하기 전에 읽는다. [Superpowers brainstorming 원본](../upstream/superpowers/skills/brainstorming/SKILL.md)을 먼저 읽고 해당 경로의 절차를 따른다. 버전과 라이선스는 [원본 잠금 파일](../upstream/superpowers/upstream.lock.json)에 있다. 원본은 수정하지 않고 이 문서에서 Codex 대화와 AX 실행의 연결만 정의한다.

## 원본 대화 경험

사용자의 언어로 대화한다. 먼저 작업을 spike(가능성 조사), bounded(기존 흐름의 작은 변경), architectural(신규 프로젝트·구조 변경)로 분류해 알려준다. 새 프로젝트를 단순하다는 이유로 bounded로 낮추지 않는다. 숨은 복잡성이 드러나면 원본 규칙대로 경로를 올린다.

목적·대상 사용자·성공 기준·제약을 확인한다. 이미 받은 답은 다시 묻지 않는다. 확인한 사실과 가정을 구분해 이해한 내용을 되짚고 수정 기회를 준다. 질문은 한 번에 하나만 한다. 선택지를 제시할 수 있으면 추천안을 먼저 두되, 사용자의 자유 답변을 받아들인다. 질문을 던진 뒤 답변 전에 계획을 대신 확정하지 않는다.

architectural 경로에서는 2~3개 접근과 장단점·추천 근거를 제시하고 설계를 부분별로 검토받는다. 대화에서 방향을 확인한 뒤 원본의 spec 작성·자체 검토·사용자 문서 검토를 거친다. 원본의 written spec 검토 전에는 구현 태스크 Plan을 만들거나 apply/run하지 않는다. 인터뷰에 필요한 저장소 읽기와 브레인스토밍 시각 자료는 가능하지만 제품 구현·스캐폴딩·제품 의존성 설치는 시작하지 않는다.

bounded는 짧은 대화 설계 검토 후 기존 실행 범위 안에서 Plan으로 변환한다. 별도 긴 spec·계획 문서를 강제하지 않는다. spike는 승인된 조사와 결론까지이며 결과 코드를 제품 구현으로 자동 승격하지 않는다. 조사 자체가 코드 실행을 필요로 하면 승인된 probe 범위에서만 수행한다.

## 대화와 재개 기록

인터뷰는 사용자가 보고 답하는 한 대화에서 진행한다. 부모가 전담 서브에이전트에 위임한 경우 질문과 대안·설계를 사용자에게 전달하고 실제 답변을 같은 전담 에이전트로 돌려준다. 서브에이전트가 사용자 질문 도구를 직접 쓸 수 없으면 다음 질문 한 개와 현재 상태를 부모에게 반환한다. 부모의 추정 답이나 서브에이전트의 자기 승인을 사용자 답변으로 기록하지 않는다.

텍스트 질문에는 사용 가능한 사용자 질문 도구를 사용한다. 도구가 없으면 일반 대화에서 묻고 답을 기다린다. 답이 없거나 대화가 끝나면 그 상태를 보존한다. 타임아웃·무응답·단순 상태 조회를 동의로 간주하지 않는다. 새로운 요청으로 재귀 위임하지 않는다.

대상 프로젝트 `.task-agent/requests/<요청 식별자>/discovery.md`에 다음을 갱신한다. 사용자에게 양식 작성을 요구하는 대신 에이전트가 대화에서 기록한다.

- 원문, 경로 분류와 이유, 현재 단계, 다음 질문 또는 기다리는 검토.
- 확인한 목적·대상·성공 기준·제약·제외 범위, 미확정 가정.
- 질문과 실제 답변, 비교한 접근과 선택 이유, 설계 섹션 피드백.
- spec·계획 파일 경로와 각 문서를 검토받은 당시 SHA-256, 실제 사용자 답변 및 그 답변이 적용되는 단계, 이미 허용된 실행 범위.

파일은 일반 작업 기록이며 신뢰된 승인 토큰이나 엔진의 보안 장치가 아니다. 대화 재개 시 기록과 실제 대화를 대조해 가장 이른 미완료 단계부터 이어간다. 문서가 바뀌었으면 기존 답변이 변경 내용까지 승인한 것으로 간주하지 않고 영향을 받은 부분을 다시 제시한다. 기존에 검토한 문서와 범위가 그대로라면 같은 질문을 반복하지 않는다.

기본 문서 위치는 원본대로 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`와 `docs/superpowers/plans/YYYY-MM-DD-<topic>.md`다. 사용자가 지정한 위치가 우선한다. 문서 커밋은 해당 프로젝트가 Git 저장소이며 세션의 커밋 범위가 허용할 때만 한다. 문서 저장·검토와 원격 게시를 혼동하지 않는다.

## 원본 계획 단계에서 AX로 전달

architectural spec의 사용자 검토가 끝나면 [Superpowers writing-plans 원본](../upstream/superpowers/skills/writing-plans/SKILL.md)을 읽는다. 원본처럼 구체적인 파일·인터페이스·검증 방법을 담은 작은 태스크 계획을 작성하고 자체 검토한다. spec의 제약을 각 작업에 전달한다.

이 시스템의 실행 방식은 이미 AX 격리 태스크로 정해져 있다. 원본이 요구하는 `writing-plans` 호출은 위 파일 읽기로 연결하며, 최종 `subagent-driven-development`/`executing-plans` 호출은 [우리 계획 변환](planning.md)과 AX 엔진 호출로 대체한다. 사용할 수 없는 외부 스킬을 호출하거나 호스트 직접 구현으로 우회하지 않는다. 계획 머리말의 실행 지침도 AX 진입점으로 작성한다.

원본의 테스트 작성→실패 확인→구현→통과 확인은 각 leaf 내부 단계다. 각 작은 셸 명령을 독립 actor로 분리하지 않는다. leaf는 검증 가능한 결과 하나를 소유하고, 각 계획의 Consumes/Produces를 Plan inputs/outputs에 연결한다. 독립 validator는 계획에 고정하며 구현 에이전트의 완료 메시지로 대신하지 않는다. 원본의 작업별 Git commit 단계는 Git 저장소가 없는 AX actor 내부 명령으로 옮기지 않는다. 결과 채택·내보내기 뒤 실제 대상 저장소에서 사용자가 허용한 커밋 범위로 처리한다.

계획 문서와 변환된 Plan을 사용자에게 제시해 검토받는다. 사용자가 이미 지정한 실행 방식을 다시 고르게 하지 않는다. 계획 검토와 기존 실행 범위를 확인한 뒤 validate/apply/run으로 진행한다. 계획만 요청했으면 검토 가능한 문서와 Plan까지 만들고 실행하지 않는다. “방향이 좋다”는 답변을 아직 작성하지 않은 spec이나 계획의 승인으로 확대하지 않는다.

## 시각 보조 도구

그림을 보아야 판단하기 쉬운 질문이 실제로 생길 때만 원본대로 별도 메시지로 사용 의사를 묻는다. 수락하면 [원본 visual-companion](../upstream/superpowers/skills/brainstorming/visual-companion.md)을 읽고 동봉한 scripts를 사용한다. 먼저 켜두거나 모든 질문을 시각화하지 않는다.

원본의 상대 경로 `skills/brainstorming/...`는 이 스킬의 `upstream/superpowers/skills/brainstorming/...`에서 찾는다. 원본이 제공하는 `SUPERPOWERS_DISABLE_TELEMETRY=1` 환경 설정으로 외부 브랜드 이미지 요청을 끈다. start-server.sh는 그 디렉터리를 기준으로 실행하고 `--project-dir`은 실제 대상 프로젝트를 지정한다. Codex에서 프로세스를 유지하려면 필요에 따라 `--foreground`와 세션을 반환하는 실행 도구를 사용한다. `.superpowers/`의 세션 키와 클릭 기록은 커밋하지 않는다. 원본 stop-server.sh로 시작한 세션만 종료한다. 브라우저 클릭은 선택 자료이며 설계·계획 전체의 승인으로 자동 변환하지 않는다.

## 적용 경계

기존 그래프의 status/result/suspend/resume만 요청하면 인터뷰를 다시 시작하지 않는다. 새 목표나 의미 있는 요구 변경은 해당 설계 단계로 돌아간다. 이미 승인된 구체적 Plan을 실행하는 요청이면 승인 근거와 변경 여부를 확인해 그 지점부터 이어간다. 원본 절차보다 사용자의 명시적인 작업 범위·선호가 우선하며, 예외가 있으면 무엇을 생략했는지 기록한다.

이 흐름은 대화 스킬의 동작이다. Go 엔진은 임의 CLI 호출자의 인터뷰 이력이나 사용자 승인을 검사하지 않는다. 형식 검증과 실제 actor 중단·결과 검증의 책임은 기존 AX 엔진에 그대로 둔다.
